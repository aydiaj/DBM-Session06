    STEP 03 / 08 · 16 MINUTES

    Read an item: tracking choices

    Start with the purpose of the read

    In Session 05, we used LINQ to display inventory data. Today, we also need to retrieve an item before changing its price or deleting it. Both start with a read, but they have different purposes.

    Familiar SQL · same row for all three purposes
    SELECT * FROM dbo.Items
WHERE Id = @id;
    1Read to display

    Show an item or a report. No changes to save.

    2Read to update

    Load an item, change its price, then save.

    3Read to delete

    Load the item, check it, confirm removal, then save.

    Choose the query based on what you will do with the result, not only on the ID.

    Tracking or no tracking?

    When EF Core reads a row, it can create a C# Item from its values. This is materialisation. For a normal entity query, EF Core also remembers that object in the DbContext and tracks its values. This is tracking.

    Display only · no tracking
    var item = await db.Items
    .AsNoTracking()
    .SingleOrDefaultAsync(i => i.Id == id);
    Prepare to update or delete · tracked
    var item = await db.Items
    .SingleOrDefaultAsync(i => i.Id == id);

    Use SingleOrDefaultAsync when you expect at most one match, such as a primary key.
    Use FirstOrDefaultAsync when several records may match and you only want one (add sorting if the choice matters).
    A projection that returns only values, not entities, does not need tracking.

    Check for null

    Both single-result queries can return null when no item matches. Check the result before accessing its properties.

    Read-only result Tracked result
    C# Item in memory, or null. C# Item in memory, or null.
    Not registered in this DbContext's ChangeTracker. A newly loaded entity is tracked by this DbContext, initially as Unchanged.
    You can modify the object, but changes are not tracked or saved automatically. Use Update() followed by SaveChangesAsync() to persist them. EF Core can detect property changes and persist them with SaveChangesAsync().

    Both queries can retrieve the same row when executed. AsNoTracking() avoids unnecessary tracking for display. Normal LINQ entity queries track by default; AsTracking() can make that choice explicit.

    Your aim Tracking choice
    Show one item by ID AsNoTracking() — no changes needed
    Load one item to change or remove Tracking (default) — prepare for changes
    Search or filter items for display AsNoTracking() — read-only results
    Show a list or report AsNoTracking() — avoid unnecessary tracking

    Who owns the tracking?

    Tracking belongs to a specific DbContext instance. Each context has its own ChangeTracker.

    An entity can remain as a C# object in memory, but that does not mean it is still being tracked. When the context is disposed, its tracking information is no longer available.

    In our Console app, each menu action creates a fresh context. That context retrieves entities, performs the operation, and is then disposed.

    Web applications follow a similar idea, but usually create a separate DbContext for each HTTP request. Let's see why this matters.

    Why this matters in a web application

    Imagine an inventory website. A user opens an item's edit page but may spend several minutes reviewing or changing its price before clicking Save. We should not keep the original DbContext alive while the user is editing. Instead, the save request typically uses a new context.

    1 GET · display

    Context A reads the item data for display. The request ends, and the context is disposed.

    2 User edits

    The browser holds the new price. Context A is gone, so its tracking is no longer available.

    3 POST · save

    A new request uses Context B. It retrieves the item with tracking, validates the input, applies the allowed change, and saves.

    Two requests, two contexts. Each DbContext has its own tracking information. Tracking is not shared between contexts.

    We will learn how to implement HTTP requests in a later course.

    A direct primary-key lookup: FindAsync

    Familiar SQL · illustrative
    SELECT * FROM dbo.Items
WHERE Id = @id;
    EF Core · C#
    var item = await db.Items.FindAsync(id);

    When you need a tracked entity and know its primary key, FindAsync is a convenient alternative to the tracked LINQ query. If the key is already tracked in this context, it returns that object without another query. Otherwise it queries SQL Server; a missing key returns null.

    Use LINQ instead for no-tracking reads, extra conditions, projection or related-data queries. FindAsync itself is a primary-key operation, not a composable LINQ query.

    Where does FindAsync look first?

    FindAsync(id) looks for an entity by its primary key. It checks the tracked entities in this context before sending a query to SQL Server.

    1FindAsync(1)

    Search the context for an Item with key 1.

    2Already tracked?

    Yes: return the same object, with no new SQL query. No: query SQL Server.

    3If a row is found

    Materialise and track it as Unchanged. If no matching row exists, return null.

    Same context · two references
    var first = await db.Items.FindAsync(1);
var again = await db.Items.FindAsync(1);

if (first is not null)
    Console.WriteLine(ReferenceEquals(first, again)); // True

    ReferenceEquals checks whether two variables refer to the same C# object. It is not comparing two database rows.

    Does FindAsync always read the current database values?

    No. If the same key is already tracked, it can return the current in-memory values, even if they are unsaved. For an independent read of the stored row here, use AsNoTracking with a LINQ condition. A new DbContext has its own tracker. A normal tracking LINQ query can execute SQL but still reuse a tracked object.

    Which rows are actually tracked?

    Our database has many Items. Creating a context does not load them all. A DbSet gives access to the table through EF Core; it is not a list of every row in memory.

    SIMULATED DATABASE · 4 of the familiar rows
    4Stored rows
    0Objects in memory
    0Tracked entries
    Stored in SQL Server C# object in memory Change Tracker entry
    1 · Top Gun
    18.00    		 Not loaded None
    2 · Star Wars
    20.00    		 Not loaded None
    3 · Star Trek
    12.50    		 Not loaded None
    4 · The Godfather
    25.00    		 Not loaded None
    A new context has no tracked objects yet.
    C# action · illustrative
    using var db = new InventoryDbContext(options);

    After the three read operations, three C# objects exist in memory, but only two are tracked by this DbContext. The third object is not tracked. The Godfather was not retrieved at all; its row still exists in SQL Server.

    Tracked does not mean Modified. Top Gun and Star Trek initially have the Unchanged state because they were retrieved through tracking queries. However, tracking means EF Core monitors an entity; its state determines whether an INSERT, UPDATE, or DELETE is needed when saving changes. For example, Add() starts tracking a new entity as Added, marking it for insertion when SaveChangesAsync() is called.

    Choose tracking based on your goal. Entity queries track by default unless configured otherwise. Use AsTracking() to explicitly request tracking, or AsNoTracking() when tracking is unnecessary, such as displaying reports. Tracking is generally preferred when retrieving, editing, and saving an entity with the same DbContext.

    Can we change the default tracking behavior?

    Yes. EF Core tracks entity queries by default (TrackAll). We can change this default through DbContextOptionsBuilder.

    DbContext configuration · optional 
    optionsBuilder
    .UseSqlServer(connectionString)
    .UseQueryTrackingBehavior(QueryTrackingBehavior.NoTracking);

    Now, entity queries use no tracking by default. Individual queries can still override this setting:

    Override for one query 
    var item = await db.Items
    .AsTracking()
    .SingleOrDefaultAsync(i => i.Id == id);

    Remember: This configuration changes the default for LINQ entity queries, not every EF Core operation. For example, FindAsync() still returns a tracked entity.

    Try this prediction

    If you edit a tracked Top Gun object, EF Core can detect and save the change. If you edit the untracked Star Wars object, SaveChanges does not automatically write that edit. The unloaded row has no C# object to edit in this example.

    Inside EF Core: who does what?

    Think of EF Core as the bridge between your C# objects and SQL Server. A DbContext is the working area for one database task.

    C# applicationCreates and uses one InventoryDbContext instance.
    ↓
    EF CoreMicrosoft.EntityFrameworkCore
    InventoryDbContextOne context instance · one unit of work
    ENTITY SETDbSet<Item>db.Items

    Build queries and register entity operations.

    SHARED TRACKERChangeTrackerdb.ChangeTracker

    Tracks entity instances and their states in this context.

    SAVE METHODSaveChangesAsync()db.SaveChangesAsync()

    Detects and saves all pending tracked changes.

    All entity sets in this context share the same tracker. Save is a method on the context, not on a DbSet.
    ↓

    Queries and save operations use the configured provider.

    SQL Server providerMicrosoft.EntityFrameworkCore.SqlServerTranslates supported queries and database changes for SQL Server.
    ↓
    Microsoft.Data.SqlClientDriver: connects and sends commands.
    ↓
    SQL ServerStores the real rows and executes SQL.

    Who owns change tracking? EF Core provides it; each DbContext instance has its own ChangeTracker. It is not a SQL Server feature and is not part of the SQL Server provider. The provider is needed for database-specific queries and commands.

    See the two paths: read and save
    ReadDbSet query→Provider / driver→SQL Server

    Returned row values become C# objects; normal entity queries then track those objects.

    SaveDbContext→Detect pending changes→Provider / driver / SQL Server

    Change tracking helps decide what to write. It does not send SQL itself.

    STEP 04 / 08 · 14 MINUTES

    Create and save an item

    Create starts in memory

    Familiar SQL · illustrative
    INSERT INTO dbo.Items
    (Name, UnitPrice, Stock, IsActive, AddedAt)
VALUES (@name, @price, @stock, @active, @addedAt);
    EF Core · C#
    var item = new Item { /* property values */ };
db.Items.Add(item);
await db.SaveChangesAsync();

    The SQL statement is illustrative. The database-generated identity value is returned to EF Core after a successful insert.

    Three moments in an insertion

    1New Item

    C# object exists. No row yet. State: Detached.

    2Add

    EF Core starts tracking the new Item. State: Added. Still no row.

    3Save

    EF Core inserts the row; SQL Server provides its ID. State: Unchanged.

    The new Item { ... } syntax creates an object and fills its properties. Add() schedules an insertion. It is not the same as executing SQL INSERT.

    Identity key

    Leave Id at its default value. EF may track a temporary key internally; the real generated Id is available on item.Id after a successful save. Never predict it.

    STEP 05 / 08 · 16 MINUTES

    Update a tracked entity

    The powerful part: implicit update

    Familiar SQL · illustrative
    UPDATE dbo.Items
SET UnitPrice = @newPrice
WHERE Id = @id;
    EF Core · C#
    var item = await db.Items.FindAsync(id);
if (item is not null)
{
    item.UnitPrice = newPrice;
    await db.SaveChangesAsync();
}

    No call to Update(). The context already tracks the returned entity. Saving normally detects changes and produces the appropriate UPDATE.

    How does EF Core know?

    The Change Tracker keeps an original snapshot and uses the tracked object’s current values. Compare the three different places:

    C# OBJECT

    Current value

    25.00item.UnitPrice
    CHANGE TRACKER

    Original value

    12.50Detect changes → Modified
    SQL SERVER

    Stored value

    12.50Until saving succeeds
    1Retrieve

    EF tracks the existing Item as Unchanged.

    2Edit

    Change its price in memory. Database unchanged.

    3Save

    DetectChanges compares values. SQL Server is updated.

    With normal snapshot tracking, the reported state may remain Unchanged until detection. Some inspection APIs trigger detection. SaveChangesAsync normally does it automatically.

    Do not call Update() here

    Update() is an explicit way to mark an entity for updating and can mark more properties modified. It is unnecessary for an Item we just retrieved with tracking. Avoid creating an incomplete new object just to overwrite an existing row.

    How long is a context alive?

    Tracking belongs to the current context, not the Item class or SQL Server. If it is disposed without saving, the pending update is not stored. A C# object can still exist if your code keeps a reference to it.

    STEP 06 / 08 · 12 MINUTES

    Confirm and delete

    Delete means remove a stored row

    Familiar SQL · illustrative
    DELETE FROM dbo.Items
WHERE Id = @id;
    EF Core · C#
    var item = await db.Items.FindAsync(id);
if (item is not null)
{
    // Ask for confirmation first.
    db.Items.Remove(item);
    await db.SaveChangesAsync();
}

    Remove marks an existing entity as Deleted. SQL DELETE is normally executed at the save boundary.

    Do it safely

    1Find

    Know which exact row will be deleted.

    2Confirm

    Show the name and key. Continue only after YES.

    3Remove & save

    Deleted → successful save → Detached.

    Do not delete the seed records. The supplied menu rejects IDs 1–16 for all update/delete options. Deleting a freshly created practice item lets you verify the whole lifecycle.

    Remove is not the same as DELETE right now

    Before saving, the stored row still exists. After saving, the deleted entity normally becomes Detached; a reference to the C# object may still exist. Removing a new Added entity before saving cancels the pending insert.

    Explore change tracking

    Five entity states

    Entity state is EF Core’s view of one object within one DbContext.

    State Meaning Typical save
    Detached Not tracked by this context. No automatic write
    Added New entity scheduled for insertion. INSERT
    Unchanged Tracked, no detected differences. None
    Modified Tracked entity has detected changes. UPDATE
    Deleted Existing tracked entity scheduled for deletion. DELETE

    Save boundary: After default successful saving, Added and Modified normally become Unchanged. Deleted becomes Detached. SaveChangesAsync returns the number of state entries written, not necessarily the exact number of SQL rows affected.

    Common questions about saving

    Check these small differences before moving on.

    Does SaveChanges save the entire database?

    No. It saves pending tracked changes in this context across its DbSets. Unchanged entries and objects not tracked by the context are not updated simply because they were read.

    Why is there no SaveChanges after a normal read?

    Reading only materialises data. An ordinary tracked query starts tracking but normally does not create a pending write. SaveChanges with no pending changes returns zero.

    Why are Add and Remove not awaited?

    They normally register changes in memory. SaveChangesAsync performs the database write. Some specialized key generation may need asynchronous AddAsync; the SQL Server identity-key lab uses Add.

    What if I change the price and then call FindAsync for the same ID?

    It can return the same locally tracked object, including a new price that has not been saved. A separate no-tracking LINQ read can show the actual stored value. SaveChanges is what makes the change persistent.

    What if SaveChanges returns zero or fails?

    Zero may mean no pending detected changes (for example, assigning the same price). The return value counts state entries written. On an exception, do not report success; read the stored result and check the error. Do not confuse saving with a schema migration.

    Data versus schema

    SaveChangesAsync() persists added, modified and deleted records. It does not create a new table or add columns to a model’s database schema. Schema changes are managed separately through migrations.
